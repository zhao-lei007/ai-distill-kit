# 每周蒸馏判读提示词

把下面整段作为指令，附上本周提取出的「用户手打消息」列表，交给模型判读。也可以直接由助手在会话内执行。

---

你在为一个岗位知识库做每周判读。输入是用户过去一周对 AI 助手手打的消息，每条附有日期、来源项目、原文。你的任务是判断每条消息里有没有**可迁移的知识**，并给出合并动作。

## 一、要收的和要丢的

**要收**（换一个项目、换一个人来做，这句话仍然成立）：

- 业务口径：某个指标怎么算、某类数据怎么理解、什么情况算异常
- 处理规则：遇到某种情况先做什么后做什么、哪些坑要绕开
- 判断依据：为什么选 A 不选 B、什么条件下方案要换
- 协作规矩：和谁对接、什么节点要确认、交付物长什么样
- 工具用法里的踩坑：某个工具在特定条件下的非显然行为

**要丢**（只在这一次、这一个对象上成立）：

- 配置信息：某个具体的 ID、路径、账号、表名、字段名本身
- 任务指令：「帮我改一下」「重新跑」「看看结果」
- 情绪和寒暄
- 粘贴进来的日志、报错、代码
- 已经写在项目文件（project.md、README）里的内容

**边界情况**：一条消息既含具体 ID 又含规则，例如「指标 M-1024 遇到分母为零要显示为空而不是 0」。做法：把 ID 泛化掉，保留规则（「比率类指标分母为零时显示为空，不显示 0」），置信度封顶 medium，来源里注明「由具体案例泛化」。

## 二、置信度分流

| 置信度 | 判据 | 去向 |
|---|---|---|
| high | 用户明确以规则口吻陈述，或同一判断在不同项目、不同日期出现 2 次以上 | 直接写入正式文件 |
| medium | 单次出现但表述清晰，或由具体案例泛化而来 | 观察池 |
| low | 只是倾向、疑问、或语境不足 | 观察池，标 low |

观察池条目 56 天内在新会话里再次出现，晋升到正式文件；56 天不复现，标「过期」移到观察池末尾。

## 三、合并动作（每条只选一个）

| 动作 | 触发条件 | 写什么 |
|---|---|---|
| 新增 | 正式文件里没有同义条目，置信 high | 新条目，编号顺延，首次记录 = 消息日期 |
| 入池 | 置信 medium/low，观察池里没有 | 观察池新条目 |
| 晋升 | 观察池里已有，本周复现 | 移入正式文件，首次记录保留池内日期，最近确认 = 本周 |
| 复现 | 正式文件里已有，本周再次出现且一致 | 只更新「最近确认」日期 |
| 更新 | 正式文件里已有，本周说法更具体或有补充 | 改写内容，保留编号，最近确认 = 本周，CHANGELOG 记一行 |
| 冲突 | 正式文件里已有，本周说法相反 | 不改原条目，在条目下加「冲突待裁决」块，列两种说法和各自日期，交用户 |
| 阶段性 | 用户明说「这个先这样」「暂时」「等 X 之后再改」 | 条目标「阶段性」，90 天后提醒复核 |
| 池内过期 | 观察池条目距首次记录超过 56 天且本周未复现 | 移到观察池末尾，标「过期」 |

判断「同义条目」时按含义比对，不要求字面相同。拿不准是「更新」还是「冲突」时，按冲突处理，交给用户。

## 四、输出格式

对每条输入消息输出一行 JSON，字段：

```
{"date": "2026-09-01", "project": "项目A", "verdict": "keep|drop", "reason": "一句话",
 "category": "分类名", "confidence": "high|medium|low", "action": "新增|入池|晋升|复现|更新|冲突|阶段性|丢弃",
 "knowledge": "泛化、脱敏后的一句话知识", "matches": "已有条目编号或空"}
```

全部判完后，再输出一段给用户看的摘要：本周读了多少条、手打多少条、各动作各多少条、需要用户决策的列表（冲突、阶段性到期、待复核）。

## 五、你不能做的

- 不能把任何条目标为「已失效」。
- 不能删除已有条目。
- 不能因为某条知识「看起来不重要」就丢弃，重要性由用户定。
- 不能把配置信息原样写进知识文件，哪怕它出现了很多次。
